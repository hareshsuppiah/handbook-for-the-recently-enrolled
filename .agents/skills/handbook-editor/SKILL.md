# Handbook editor

Use this skill for editorial and reading-experience work in this repository. Read root `AGENTS.md`, `PRODUCT.md`, `DESIGN.md`, the affected page and linked practical resources. It does not require access to Haresh's personal skills. A wording correction needs a proportionate check; a new chapter needs source research and coverage review.

## Start with the reader's difficulty

State privately what the reader should understand or be able to do after the change. Read the surrounding section before drafting. Inventory the citations, claims, local-policy caveats, stop conditions and links that must survive. For a removal, identify where the useful material will go or why it is superseded.

Lead with a recognisable situation. Explain the idea before asking the reader to complete a checklist. A small hypothetical example can show the decision; do not fabricate a student story, result or citation. Prefer ordinary verbs to abstract labels: “what this study can tell you” before “scope of inference”. Let the cadence vary. Avoid repeating a mandatory opening question, warning box, five-part framework and summary on every page.

A welcome should not become empty reassurance. Preserve firm language where privacy, consent, integrity or safety requires it. Help-seeking does not depend on completing a perfect record first. Include variation in study mode, method and discipline where it changes the advice; do not append token lists of identities.

## Research and connect

Read sources for new substantive claims. Distinguish empirical evidence, practical suggestion, philosophical interpretation and local policy. Record source URL/DOI, checked date, supported wording and limits using [the evidence note](references/evidence-note.md). Existing references are not permission to extend claims beyond their support. Preserve unresolved author/citation placeholders unless asked to resolve them.

A chapter should lead to a useful next action and an appropriate resource. A checklist separates independent tasks from alternative decisions. Unknown and not-applicable answers need handling; a tick cannot authorise consequential work. A template supplies one blank reusable text block inside `<details class="template-copy">`, followed by clearly marked illustrative examples if useful. A collapsed plain-text copy can accompany a readable table; keep its fields and safeguards consistent with that table. Do not add competing forms with different requirements.

## Add interaction only when it teaches or helps reuse

Use native `<details>` with a specific `<summary>` for an optional worked answer. Put important warnings outside the disclosure. Do not quiz or grade judgement where several defensible answers exist. Static text and links remain complete without scripts. `assets/reader/reader-tools.js` supplies reusable checklist, page feedback, template and finder controls; extend that shared system only when the authorised scope needs it. Keep text drafts out of storage. Preserve keyboard focus, status messages, narrow-screen usability and print output.

Images need a specific teaching role, useful alternative text and verified reuse rights. Dated GitHub screenshots supplement text and should show current visible controls. No fabricated screens, image quotas or automatic humour on sensitive routes. Use the visual register and existing generator when changing comic placements.

## Review and finish

Read the edited passage aloud in your head as a capable person helping one student. Compare citations, caveats, claims and links with the original; check heading anchors. Run root `AGENTS.md`'s relevant verification commands. Inspect the rendered page, and interactions if changed. Report the evidence actually obtained and any checks that remain unavailable. Follow the existing authorisation for commit/publication; an approved issue alone still ends at a tested pull request.
